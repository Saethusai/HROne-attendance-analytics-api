# REVIEW.md

List every defect found in the starter `app/main.py`. For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` / line 35 | `punch_in.replace(hour=h, minute=m)` anchors `shift_start` to the **punch-in's calendar date**, not the **attendance date**. For overnight shifts (e.g. 22:00–06:00), an employee punching in at 00:15 IST has attendance date = previous day, so shift_start should be on the previous day. Using punch_in's date places it on the wrong day, producing incorrect late_minutes. | `POST /attendance/punch-in` for EMP0005 (shift 22:00–06:00) with a punch-in just after midnight IST: late_minutes comes back 0 when it should reflect the correct offset from 22:00 on the previous day. | Fixed: `shift_start` is built using the pre-computed `att_date` string: `datetime(d.year, d.month, d.day, sh, sm, 0, tzinfo=IST)` where `d = datetime.fromisoformat(att_date)`. |
| 2 | `compute_late_minutes` / line 37 | Condition `minutes > 10` is wrong. `minutes = int(secs/60)` floors, so 601 seconds → `minutes = 10` → `10 > 10` is `False` → returns 0, but R2 requires it to return 10. The correct check is `total_seconds > 600`. | Boundary test: shift 09:30, punch at 09:40:01 → expected `late_minutes = 10`, got `0`. | Fixed: check `diff_secs <= 600` before the floor: `return 0 if diff_secs <= 600 else int(diff_secs // 60)`. |
| 3 | `compute_work_hours` / line 41 | `round()` uses Python's banker's rounding (round-half-to-even). R4 requires half-up rounding. | Edge case: `9.125` hours → Python `round(9.125, 2)` = `9.12` (rounds to even); R4 requires `9.13`. | Fixed: replaced with `Decimal(str(value)).quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)`. |
| 4 | `compute_overtime` / line 47 | No >= 30 min minimum. R3 says overtime is counted only when `floor_minutes >= 30`; otherwise 0. | Punch out 25 minutes after shift end → `overtime_minutes = 25`, should be `0`. | Fixed: `return minutes if minutes >= 30 else 0`. |
| 5 | `compute_overtime` / line 46 | For overnight shifts (`shift_end <= shift_start`), `shift_end` falls on `att_date + 1 day` in IST. Placing it on `att_date` gives the wrong reference point and often a large negative or incorrect diff. | EMP0005 (22:00–06:00), punch out at 06:40 IST → overtime should be 40 min. With incorrect date, diff is negative. | Fixed: `end_date = att_date + timedelta(days=1)` when `is_overnight`. |
| 6 | `create_employee` / line 79–80 | Check-then-insert race condition. Two concurrent requests can both pass the `find_one` check before either inserts, resulting in both getting 201. Spec requires exactly one 201, rest 409. | Two simultaneous `POST /employees` with the same `emp_code` → both succeed. | Fixed: removed check; added unique index on `emp_code`; catch `DuplicateKeyError` → 409. |
| 7 | `create_employee` / line 82 | `datetime.now()` returns a naive datetime using the OS local timezone. On a non-IST server this is wrong; PyMongo will store it ambiguously. API response must return `created_at` as epoch milliseconds (integer), not a datetime object. | On a UTC server, `created_at` in the DB has no timezone. Serialised in the response as a Python datetime string, not an integer. | Fixed: `datetime.now(timezone.utc)` for storage; `dt_to_ms()` in `serialize_employee()` converts to epoch ms for the response. |
| 8 | `list_employees` / line 93 | `skip = page * page_size`. With `page=1`, `page_size=20`, skip=20, so the first page of results is entirely skipped. R10 says page starts at 1. | `GET /employees?page=1` returns records 21–40 instead of 1–20. | Fixed: `skip = (page - 1) * page_size`. |
| 9 | `list_employees` / line 94 | `total = db.employees.count_documents({})` ignores the `department` filter. R10: "`total` always reflects the applied filters." | `GET /employees?department=Sales` returns `total=100` (all employees) instead of the number in Sales. | Fixed: `total = db.employees.count_documents(q)`. |
| 10 | `list_employees` / line 95 | No sort. Spec says "Sorted by `emp_code` ascending." Without a sort, order is undefined and non-deterministic. | Results differ between requests on the same dataset. | Fixed: `.sort("emp_code", ASCENDING)`. |
| 11 | `list_employees` / line 95 | `created_at` returned as a Python `datetime` object. Spec requires epoch milliseconds (integer). | Response fails schema validation; clients see a datetime string, not an integer. | Fixed: `serialize_employee()` converts `created_at` via `dt_to_ms()`. |
| 12 | `punch_in` / line 101, 113 | `emp = db.employees.find_one(...)` is never checked for `None`. If the employee doesn't exist, `emp["shift_start"]` on line 113 raises `KeyError`, returning an unhandled 500 rather than the required 404. | `POST /attendance/punch-in` with an unknown `emp_code` → 500 Internal Server Error. | Fixed: `if emp is None: raise HTTPException(404, "employee not found")`. |
| 13 | `punch_in` / line 102 | `datetime.fromtimestamp(ms/1000)` uses the OS local timezone. On a UTC host the result is correct UTC, but on any other host the result is wrong. Also: `datetime.now()` (fallback) is naive. R1 requires times to be truncated to whole seconds before storage. | On a server with TZ=Asia/Kolkata, `fromtimestamp` returns IST-local naive datetime; stored in MongoDB as IST-naive, all downstream calculations are off by 5:30h. | Fixed: `ms_to_dt()` uses `datetime.fromtimestamp(ms/1000, tz=timezone.utc).replace(microsecond=0)`. |
| 14 | `punch_in` / line 103 | `d = ts.date().isoformat()` uses `ts.date()` which is in whatever timezone `ts` is (local or UTC), not IST. Also: no overnight shift rule (R1 exception). | On UTC server, a punch-in at 23:45 UTC (= 05:15 IST next day) gets attendance date = UTC date, not IST date. An overnight-shift punch-in at 00:15 IST gets the wrong date. | Fixed: `attendance_date(ts, emp["shift_start"], emp["shift_end"])` applies R1 correctly. |
| 15 | `punch_in` / line 104–105 | Check-then-insert race condition. Spec says "Do not rely on check-then-insert" and requires exactly one 201 on simultaneous punch-ins. | Two concurrent punch-ins for the same employee/date → both succeed. | Fixed: removed check; compound unique index on `(emp_code, date)`; catch `DuplicateKeyError` → 409. |
| 16 | `punch_in` / line 119 | Response adds a spurious `"id"` field (not in `AttendanceRecord` schema). `punch_in` datetime is also not serialised to epoch ms. | Response body has `"id": "..."` which the grader's schema check rejects; `punch_in` is a datetime string not an integer. | Fixed: removed `id` line; `serialize_record()` converts all datetime fields to epoch ms. |
| 17 | `list_attendance` / lines 144–146 | `list(db.attendance_logs.find(q))` loads the **entire collection** into memory before filtering, sorting and paginating. Spec says "Must stay fast on a collection of ~100,000 records; do not load the collection into memory." | With 100k records, the endpoint uses 100k × document size of RAM and is very slow. | Fixed: `count_documents(q)` for total; cursor with `.sort().skip().limit()` for the page. |
| 18 | `list_attendance` / line 145 | Sort is only by `date` descending. Spec requires secondary sort `emp_code` ascending for deterministic ordering on the same date. | Two records on the same date are returned in undefined order; grader's ordering check fails. | Fixed: `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| 19 | `list_attendance` / line 149 | Adds a spurious `"id"` field and does not convert datetime fields to epoch ms. | Schema mismatch; `punch_in`/`punch_out` are datetime strings not integers in the response. | Fixed: `serialize_record()` removes `_id`, converts all datetime fields. |

## Items reviewed and decided NOT to be defects

- `status_code=201` on `POST /employees` and `POST /attendance/punch-in` — correct per spec.
- `Optional[int] = None` for `punched_at` on `PunchInIn` — correct; spec says defaults to now.
- `IST = timezone(timedelta(hours=5, minutes=30))` — correct definition.
- The five-status `Status` enum in the starter model — correct values per spec.
